# Codex 编程实战教程：让 AI 修改代码、跑测试、修 Bug 和提交 PR

> 更新时间：2026-06-29。本文不讲空泛概念，只按一个真实开发任务拆解 Codex 的用法：读项目、改代码、跑测试、修报错、整理 PR。

很多 Codex 教程只写「它可以写代码」，但真正影响效率的是任务怎么拆、边界怎么设、结果怎么验证。下面这套流程适合 VitePress、Next.js、Python、Node、数据脚本等大多数项目。

## 实战前准备

| 准备项 | 说明 |
| --- | --- |
| 一个可运行项目 | 至少能本地安装依赖并构建 |
| 清楚的目标 | 例如新增页面、修复按钮、补测试 |
| 验收命令 | 例如 `npm run build`、`npm test`、`pytest` |
| 不可改动范围 | 例如不要改路由、不要改数据库结构 |
| 回滚意识 | 重要项目先建分支或备份 |

不要一上来就让 AI「优化整个项目」。越大的目标越容易产生无关修改。

## 一个好任务应该怎么写？

```text
请在当前项目中完成一个小改动。

目标：新增一篇文章，并确保 sidebar 和 latest 页面能看到它。
范围：只允许修改 docs/chatgpt 下的新文章和自动索引配置。
不要做：不要重构主题组件，不要删除旧链接。
验收：npm run build 通过；页面标题正确；最新文章排在前面。
输出：列出修改文件、关键逻辑、验证命令和剩余风险。
```

这个提示词包含目标、范围、禁止项、验收和输出格式，Codex 更容易稳定执行。

## 第一步：让 Codex 先读项目

不要急着让它写代码。先让它回答：

```text
请先阅读项目结构，找出文章目录、sidebar 配置、latest 页面生成方式和构建命令。
先不要改文件，只给我结论。
```

你要看它是否识别对了：

1. 文章文件放在哪里。
2. VitePress 配置在哪里。
3. sidebar 是手写还是自动生成。
4. latest 页面是否按 frontmatter 排序。
5. 构建命令是什么。

如果第一步读错了，后面改得越多风险越大。

## 第二步：限制改动范围

让 Codex 明确「最小改动」：

```text
请基于刚才的分析给出最小修改方案。
要求：
1. 只新增必要文件；
2. 复用现有脚本；
3. 保持 frontmatter 风格一致；
4. 不改变现有 URL；
5. 如果需要改配置，说明原因。
```

真正适合内容型文档站的改法，通常不是重构，而是补内容、补索引、补 sidebar、补 sitemap。

## 第三步：执行修改

执行前确认它知道验收标准：

```text
现在开始修改。完成后请运行构建命令，并检查新页面是否能被 sidebar/latest 收录。
```

如果 Codex 修改多个文件，你要重点看：

| 文件类型 | 检查点 |
| --- | --- |
| Markdown 文章 | title、description、date、updated、H1 是否一致 |
| 配置文件 | 是否只加必要链接或白名单 |
| 自动脚本 | 是否破坏原排序规则 |
| package.json | 是否无故改动依赖 |

## 第四步：让它跑测试和构建

不要接受「理论上可以」。要求它运行真实命令：

```text
请运行项目现有构建命令。失败时贴出关键错误，先分析原因再修改。
```

常见命令：

```bash
npm run build
npm run docs:build
npm test
pytest
```

构建失败时，不要让 AI 盲目大改。先定位到具体文件、具体行、具体语法。

## 第五步：修 Bug 时怎么给反馈？

把完整报错给它，而不是转述：

```text
运行 npm run build 失败，关键报错如下：
[粘贴完整错误]

请先判断是 Markdown frontmatter、链接、组件、还是配置问题。
只修改导致报错的最小范围。
```

AI 修 Bug 的质量，很大程度取决于你给的错误信息是否完整。

## 第六步：准备 PR 或上线说明

完成后让 Codex 输出：

```text
请整理本次修改说明：
1. 修改了哪些文件；
2. 新增了哪些页面；
3. 如何验证；
4. 还有哪些风险；
5. 上线后需要检查哪些 URL。
```

这一步对团队协作和内容型文档站都很有用，因为你后续要看页面是否被收录、是否进 sitemap、sidebar 是否可见。

## Codex 最适合的任务清单

| 任务 | 推荐程度 | 原因 |
| --- | --- | --- |
| 新增文章并更新索引 | 高 | 文件结构清晰，验收明确 |
| 修复构建报错 | 高 | 报错可复现，反馈闭环明确 |
| 补单元测试 | 高 | 有目标函数和预期输出 |
| 大规模重构 | 中 | 需要人工拆分阶段 |
| 生产数据库迁移 | 低 | 风险高，必须人工审查 |
| 账号、支付、安全逻辑 | 中低 | AI 可辅助，但不能直接信任 |

## 安全检查清单

1. 是否上传了密钥、token、Cookie、数据库连接串？
2. 是否让 AI 执行了删除或迁移命令？
3. 是否改动了无关文件？
4. 是否跑过构建或测试？
5. 是否人工审查了 diff？
6. 是否确认了新页面的标题、URL、内链和更新时间？

## 内容项目里的 Codex 用法

如果你在维护博客站，Codex 特别适合做这些事：

- 批量生成页面元信息。
- 检查所有文章是否有 updated 字段。
- 自动刷新 latest 页面。
- 生成 sidebar 分类。
- 找出死链和重复标题。
- 生成 Bing 提交 URL 清单。

但内容本身不要直接复制同行。更稳的打法是学习标题结构和搜索意图，正文写成自己的实操经验、对比表、FAQ 和风险提示。

## Bing 热点补强：Codex 搜索词要按开发者意图写

实战页要强调能落地的任务：读项目、改 bug、写脚本、跑测试、整理 PR。

Codex 这个词的搜索意图比较混杂：有人搜 OpenAI Codex，有人搜 ChatGPT Codex，有人找 Codex CLI 安装教程，也有人只是想知道它和 Cursor、Claude Code 有什么区别。页面要先把概念分开，再给出上手路径。

| Bing 热词 | 用户真实问题 | 本页应该回答 |
| --- | --- | --- |
| codex | Codex 是什么，和 ChatGPT 什么关系 | 先解释定位，再说明适合代码任务 |
| openai codex | 官方入口和文档在哪里 | 给出官方信息来源，不把第三方站说成官方 |
| chatgpt codex | ChatGPT 里怎么用代码能力 | 说明网页端、云端任务、CLI/IDE 的区别 |
| codex cli | 怎么安装、怎么在项目里跑 | 写清 Windows、macOS、Linux 的准备工作 |
| codex vs cursor | 该选哪个编程工具 | 用任务类型对比，而不是只写谁更强 |

## Codex 文章更容易排名的结构

| 模块 | 要写什么 | 为什么重要 |
| --- | --- | --- |
| 入口说明 | 官方入口、CLI、App、文档、GitHub 项目 | 覆盖“官网/入口/下载/安装”类搜索 |
| 实战任务 | 读代码、改 bug、写脚本、补测试、解释报错 | 开发者停留时间更长 |
| 对比表 | Codex、Cursor、Claude Code、普通 ChatGPT | 命中对比型长尾词 |
| 安全边界 | 不上传密钥、生产配置、客户数据 | 提升可信度，也适合安全类页面 |
| FAQ | Codex 能不能国内用、是否免费、是否需要 CLI | 有机会被 Bing 抽成问答结果 |

## 开发者上手路线

1. 先用一个非敏感小项目测试，让 Codex 读目录、解释架构和列出风险点。
2. 再让它只改一个小文件，不要一开始就让它大范围重构。
3. 每次修改后都要求它说明改动原因、影响范围和测试建议。
4. 重要项目里先删掉 env 文件、Token、Cookie、私有接口地址和生产日志。
5. 把 Codex 当成协作开发工具，而不是直接替你发布代码的黑盒。

### Codex 相关工具推荐：只看 ZeoGPT

Codex 主题的用户意图很集中：不是泛泛聊天，而是代码解释、项目改造、脚本生成、调试和自动化任务。因此这类文章不做多工具横向推荐，只建议优先了解 [ZeoGPT](https://www.zeogpt.com/register?ref=MRNWDKC3)。

| Codex 需求 | ZeoGPT 更适合的原因 |
| --- | --- |
| 需要 Codex 国内版入口 | 更贴近代码任务和开发者工作流 |
| 需要反复生成、解释、修改代码 | 高额度 GPT-5.5 Pro 更适合长时间跑任务 |
| 需要处理长文件、项目结构、脚本 | 比普通聊天入口更适合开发场景 |
| 需要稳定完成一组任务 | 适合“读代码 -> 改代码 -> 写测试 -> 复盘”的连续流程 |

安全边界也要说清楚：不要上传生产密钥、数据库连接串、客户数据、内部仓库完整凭证；如果要让 AI 看代码，先删掉 env 文件、Token、Cookie 和后台截图里的敏感信息。

## 追加 FAQ：Codex 搜索用户常问

### Codex 和普通 ChatGPT 写代码有什么区别？

普通 ChatGPT 更像问答式代码助手；Codex 更偏项目级工作流，适合读文件、理解上下文、修改代码、跑测试和整理变更。具体能力取决于你使用的入口和权限。

### Codex 国内版是不是官方？

“Codex 国内版”通常是第三方工具对 Codex 类能力的封装或转接，不等于 OpenAI 官方入口。官方信息应以 OpenAI 官网、开发者文档和 GitHub 项目为准。

### 使用 Codex 时最该注意什么？

最重要的是权限边界。不要上传密钥、数据库连接串、客户资料、内部后台截图和未脱敏日志；让 AI 修改代码后，也要人工 review 和跑测试。

## FAQ

### Codex 能直接提交 PR 吗？

取决于你使用的形态、仓库权限和平台功能。即便能生成 PR，也应该人工审查 diff 和测试结果。

### Codex 写的代码可靠吗？

可以提高效率，但不能免审。越涉及安全、支付、权限、数据迁移，越要人工验证。

### 最适合新手的练习是什么？

从小任务开始：让 Codex 解释一个文件、修一个明确报错、补一个测试。不要一开始就做全站重构。
